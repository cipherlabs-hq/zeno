# Retiring the Vue single-file components

`@usezeno/vue` holds 38 Vue single-file components (SFCs) from the 2025 code
base, plus an internal `BaseField`. They are a second implementation of the
same components as the Lit elements in `@usezeno/core`. Zeno keeps one
implementation, the Lit one, so each SFC goes away once its element can do the
job.

Nothing has been deleted yet. This page records, for each SFC, whether it can
go now.

## How Vue uses the elements instead

A Vue app uses the elements directly. `@usezeno/vue/elements` has what that
needs: `isZenoElement` and `zenoCompilerOptions` for the Vue compiler, template
types for every element, and `useCheckedModel` for the three elements whose
state is `checked`. `examples/vue` is a working app, and its tests show plain
`v-model` working on `zeno-input` and `zeno-select`.

## How to read the table

- **Can it be retired?**
  - **Yes**: the element covers what the SFC does. What differs is a renamed
    prop or slot, listed in the notes.
  - **After the gaps**: the element covers the main job. The notes list what
    the SFC does that the element does not. For each gap, either add it to the
    element or decide Zeno does not need it. Then retire the SFC.
  - **Not yet**: the SFC does much more than the element. Retiring it now
    would remove features.
- **Only in the SFC** comes from a script that compared the names of the props,
  events and slots each SFC declares with the names in the element's manifest.
  A name on this list can still exist in the element under another name. The
  notes call out the renames found by reading the code. Every SFC also
  declares `density`, `glass` and `motionIntensity`. No element has them, and
  the table leaves them out.
- **Lint findings** are the problems that the rules switched off for these
  files in `eslint.config.js` would report: 38 accessibility findings,
  15 uses of `any` and 12 prop-default findings in these 38 files, plus
  one accessibility finding in `BaseField`.
- **Has tests** says whether the SFC has a Vitest spec. Those specs go when
  the SFC goes.
- **Brings in** lists the third-party packages only that SFC needs.

The comparison is by declared names and by reading the code. Nobody has run
the two implementations side by side, so treat a **Yes** as "no known gap",
not as a tested guarantee.

## What goes with the SFCs

When the last SFC is gone, these go too:

- `@usezeno/styles` (Sass variables that only the SFCs use) and
  `@usezeno/composables`.
- The dependencies `@vuepic/vue-datepicker`, `@tanstack/virtual-core` and
  `lucide-vue-next`.
- The lint rule overrides for `packages/vue/src/components` in
  `eslint.config.js`.
- The dark-theme problem in the SFC styles: they contain colours that Sass
  computed from the light theme at build time.

`@usezeno/vue` then contains only the `elements` entry point.

## Suggested order

1. Retire the **Yes** rows. Each is a deletion plus a line in the changelog
   that names the renamed props.
2. Go through the **After the gaps** rows with the owner and mark each gap
   "add to the element" or "drop".
3. Decide the scope of the five **Not yet** components. The data table and the
   date picker are the large ones: both lean on a third-party Vue library.
